# MuxMender 20261001-v48

## GPU scheduling that learns from the work

This release includes the corrected v47-r3 cancellation behavior and adds
adaptive GPU-stage admission to the shared processing engine.

- GPU work starts serially, independently of CPU validation admission.
- Comparable stages are grouped by video profile, codec/filter settings and
  duration. Three serial measurements and sustained headroom are required
  before trying two GPU stages while work is waiting.
- Two stages remain allowed only after three substantially overlapping
  measurements show at least 10% more estimated aggregate stage throughput.
  Brief overlap is not counted as fully parallel work.
- GPU-engine load, VRAM, temperature, CPU, memory, storage pressure and
  GPU-sharing requests control backoff. Quiet-mode new workers stay serial.
- The dashboard shows the current GPU-stage limit and its reason.

Existing work drains when the limit drops. Publication remains in its separate
pool and is never interrupted by this policy. Quality checks, codec settings,
savings rules, cancellation and source replacement safeguards are unchanged.

## Processing-error corrections (r2)

- Source preflight and final candidate audio checks now share a discard-only
  sample clock. Duplicate packet timestamps no longer cause the null-output
  muxer to reject otherwise valid audio. Corrupt samples still fail strict
  decoding, and independent copied-packet and timing checks remain required.
- Complete original HDR frame evidence is collected before full encoding,
  checked for completeness and source changes, then reused by finalization
  and validation. This prevents spending an encoding pass before discovering
  that the original HDR read exceeds the selected processing time limit.
  It does not make that read faster or silently increase the user's limit.

## Qualification limits

Policy, cancellation and Linux OS-lock regressions were exercised with generated
or simulated work. They are not evidence of faster real-file conversion. The
production GPU was fully occupied during preparation, so a competing throughput
benchmark was not run. Hardware and completed-file performance remain pending.
See [adaptive admission](../../docs/adaptive-gpu-admission.md).

## Build after the current run

Image tag: `muxmender-app:20261001-v48-r2`.
The staged build script uses a new build directory and isolated runtime,
dashboard, process-reaping and generated NVIDIA encode smoke checks. It does
not switch the production app, resume the queue or modify media.

After image checks pass, change the app image and retain existing media/output
mounts, GPU assignment, UID/GID, port and GPU-monitor settings. Keep the output
folder: queue history, replacement receipts and scheduler evidence live there.
The persistent host-monitor installer remains bundled; an already working
installation does not need to be replaced again.
