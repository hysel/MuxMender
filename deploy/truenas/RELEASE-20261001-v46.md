# MuxMender 20261001-v46

## Faster processing with the same checks

The shared workflow chooses two or four workers for progressive eight-bit SDR
processing when measured resources permit. It also bounds FFmpeg worker pools,
avoids hashing unused video packets during small copied-track checks, and
coordinates CPU validation and GPU work. Quality, timing, metadata and savings
requirements stay unchanged. Other video profiles retain their existing paths.

The two-file research batch finished in **35.44 instead of 56.55 minutes**,
37.33% less observed time. The full conversion passed validation with the same
75.18% size reduction, selections and sample results. Shared-host load and run
order affect these figures. The smaller job waited longer for GPU admission;
this is a batch improvement, not a guarantee that every file finishes sooner.

Faster HDR frame-threaded reading and direct NVIDIA decoding were tested and
rejected for this release. Existing HDR metadata checks remain in place.
See [measured results](../../docs/performance-results.md) for evidence and limits.

## Reliability and feedback

- Dashboard polling uses cached responses and one discovery task at a time.
- Stage reporting separates processing, resource admission and GPU-sharing pauses.
- Retry labels show the current attempt without presenting the prior result as
  an active error. Processing time limits remain selectable by the user.
- The container starts through tini to reap orphaned processes and forward
  shutdown signals. This requires smoke testing in the built image.
- The portable package includes the shared GPU-activity and pause modules.
- Audio preflight avoids discard-muxer timestamp false failures while retaining
  strict decoding and independent source/output timing checks.

The final performance snapshot passed 103 Linux tests before full-file work.
Separate cancellation, cleanup, resource-admission and monitoring tests passed
within their documented scopes. Research copies did not replace source media.

## Build and deployment

Build tag: `muxmender-app:20261001-v46`. The staged build script checks the package
checksum, builds an exclusive versioned context, and runs isolated image tests.
It does not update the existing TrueNAS app or resume the production queue.

After all image tests pass, change the app image to this tag. Preserve the
existing media/output mounts, UID/GID, GPU assignment, port and GPU-monitor
settings. Drain active jobs before changing the image. Begin with a small batch
and inspect its results before resuming the larger queue.

Existing queued requests retain their saved options and processing budgets.

## GPU monitor package update

The refreshed package includes a self-contained host monitor installer. It
embeds the matching collector, registers the TrueNAS Post Init task, and uses
`/var/lib/muxmender-gpu-monitor` for telemetry so normal reboots do not remove
the mount source. See [GPU sharing setup](../../docs/gpu-monitor-setup.md).
This host helper can be installed independently of the already validated v46
container image. Existing installations must change their telemetry Host Path
from `/run/muxmender-gpu-monitor` after running the new installer.
