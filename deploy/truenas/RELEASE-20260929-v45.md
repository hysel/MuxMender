# MuxMender 20260929-v45

## Clearer controls and progress

- Choose the processing limit under **Add videos → Encoding options**: 1–1440
  minutes per long stage, default 120. The CLI uses `--timeout-minutes`.
- New requests save the chosen budget. Existing queued jobs keep their previous
  settings; older jobs default to 120 minutes. Waiting for a validation slot does
  not consume this budget. Short tool checks and stalled-encoder protection keep
  their separate safety limits.
- Reader timeout messages identify the stage, limit and last measured progress.
  A timeout is not a quality verdict and cannot approve source replacement.
- Active retries say **Retry in progress** or **Retry queued**. Earlier results
  remain in **Previous attempts**, not beside the live retry label.
- Public documentation and the batch-review picker use generic
  **Dolby Vision-capable TV** wording rather than a specific TV brand/model.

## HDR evidence collection

The automatic workflow and HDR preservation finalizer share bounded, adaptive
thread selection. Compact JSON retains every decoded frame field and HDR
side-data value while reducing evidence-file size. No quality, timing, metadata
or savings threshold is relaxed. The faster frame-threaded reader remains
research-only; this release retains the metadata-preserving slice reader.

These changes do not claim a full-job speedup. See
[processing time limits](../../docs/processing-timeouts.md) for scope and evidence.

Targeted Linux regression: 208 passed, six platform/dependency skips. Local
UI/navigation/batch-review checks: 16 passed. These are automated tests, not
formal accessibility certification or a new full-file playback approval.

## Deployment and retry

Build `muxmender-app:20260929-v45` using the supplied build context. Preserve
mounts, UID/GID, GPU assignment, port and host GPU-monitor configuration.
The build script does not deploy or restart the app. Drain active jobs before
changing the app image if you want to avoid interrupting their work.

After deployment, select the failed source or folder, choose **Retry skipped/failed
files only**, set the desired per-stage time limit and review the request before
queuing it. Merely resuming an old request does not change its saved budget.
This release does not automatically retry failures or replace files.
